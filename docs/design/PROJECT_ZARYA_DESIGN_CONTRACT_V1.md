# Project Zarya Design Contract v1

## 1. Статус решения

**Принято.**

Project Zarya переходит на единую гибридную дизайн-систему.

Визуальной основой является последний согласованный
сбалансированный enterprise-коллаж.

Полный одномоментный редизайн не выполняется. Изменения
внедряются поэтапно, с отдельными semantic, visual и
regression-подэтапами.

Ветка первого этапа:

`feature-design-system-foundation-v1`

Дата принятия решения: 25 июля 2026 года.

## 2. Основное направление

Все страницы Project Zarya должны восприниматься как части одного
корпоративного продукта.

Общими для проекта являются:

- AppShell;
- боковая навигация;
- верхняя панель;
- типографика;
- цветовая семантика;
- сетка отступов;
- кнопки;
- поля форм;
- карточки;
- фильтры;
- таблицы;
- badges;
- статусы;
- модальные окна;
- состояния загрузки;
- empty states;
- responsive-поведение.

При этом разные бизнес-задачи используют разные типы рабочего
пространства.

## 3. Три типа рабочего пространства

### 3.1. List workspace

Применяется для:

- документов к оплате;
- журнала загрузок;
- реестров;
- справочников;
- пользователей;
- заявок;
- проверки реквизитов;
- документов, не найденных в 1С;
- системных списков.

Структура:

1. компактный заголовок страницы;
2. главное действие;
3. краткая сводка или быстрые вкладки;
4. фильтры;
5. таблица или список;
6. массовые действия;
7. пагинация и итоговые значения.

Главная задача — быстро находить, сравнивать и обрабатывать записи.

### 3.2. Analytics workspace

Применяется для:

- панели управления;
- графика платежей;
- финансовой аналитики;
- отчётов;
- реализации молока;
- контроля OCR;
- контроля импорта 1С;
- мониторинга системных процессов.

Структура:

1. ключевые показатели;
2. блок «Требует внимания»;
3. задачи пользователя;
4. графики и динамика;
5. проблемные документы;
6. быстрые действия.

Главная задача — показать не все доступные показатели, а то, что
изменилось, требует внимания или предполагает действие.

### 3.3. Context workspace

Применяется для:

- карточки документа;
- OCR-проверки;
- загрузки документов;
- согласования;
- привязки контрагента;
- проверки реквизитов;
- карточки контрагента;
- проверки реестра.

Структура:

1. основной объект или оригинал документа;
2. контекстная панель;
3. распознанные данные;
4. подтверждённые данные;
5. источник каждого значения;
6. история изменений;
7. закреплённая панель действий.

Главная задача — завершить работу с объектом без лишних переходов
между страницами.

## 4. Эталонная страница

Первой эталонной страницей дизайн-системы является:

**«Документы к оплате».**

На ней должны быть окончательно определены:

- PageHeader;
- главное действие;
- блок показателей;
- быстрые вкладки;
- FilterPanel;
- DataTable;
- статусы;
- массовые действия;
- действия строки;
- пагинация;
- desktop-режим;
- tablet-режим;
- mobile card mode.

После принятия этой страницы её компоненты распространяются
на остальные страницы типа List workspace.

## 5. Визуальный язык

Целевой интерфейс:

- тёмный;
- строгий;
- современный;
- компактный;
- спокойный;
- ориентированный на длительную ежедневную работу;
- без чрезмерного свечения;
- без декоративной перегрузки;
- с ясной визуальной иерархией.

Используются:

- тёмные нейтральные поверхности;
- тонкие границы;
- умеренные скругления;
- фирменный зелёный как смысловой акцент;
- компактная читаемая типографика;
- небольшое количество уровней глубины;
- единый ритм карточек и панелей.

Макеты являются направлением и не требуют буквального копирования.

## 6. Визуальная иерархия страницы

На каждой странице должно быть однозначно понятно:

1. где находится название страницы;
2. какое действие является главным;
3. каково текущее состояние;
4. что требует внимания;
5. где расположен основной рабочий контент;
6. где находятся вторичные действия.

Рабочие страницы не используют крупные декоративные hero-блоки.

Повторяющиеся заголовки страницы не допускаются.

На странице должно быть не более одного основного Primary-действия.

## 7. Типографика

Целевые ориентиры:

- заголовок страницы: 28–34 px;
- заголовок секции: 18–22 px;
- основной текст: 14 px;
- вторичный текст: 12–13 px;
- табличный текст: 13–14 px;
- подписи и метаданные: не меньше 12 px.

Интерфейс должен быть компактным, но не мелким.

Текст, обязательный для принятия решения, не может использовать
слабую контрастность.

Суммы должны поддерживать tabular numbers.

## 8. Сетка отступов

Основная шкала:

- 4 px;
- 8 px;
- 12 px;
- 16 px;
- 24 px;
- 32 px.

Случайные значения допускаются только при конкретной технической
необходимости.

Целевые высоты:

- обычное поле или кнопка: 40–44 px;
- компактная строка таблицы: 44–48 px;
- стандартная строка таблицы: 48–56 px;
- минимальная кликабельная область: 36–40 px.

## 9. Скругления и поверхности

Целевая система:

- badges и небольшие элементы: 8 px;
- поля и кнопки: 10–12 px;
- внутренние панели: 12 px;
- крупные карточки: 14–16 px.

Чрезмерно круглые карточки и pill-кнопки не используются без
функциональной причины.

Все карточки должны использовать согласованные:

- фон;
- границу;
- радиус;
- внутренние отступы;
- hover-состояние;
- уровень глубины.

## 10. Цветовая семантика

### Зелёный

Используется для:

- главного действия;
- успешно подтверждённого состояния;
- готовности к следующему этапу;
- успешной проверки;
- оплаченного документа.

Обычные суммы не окрашиваются в зелёный автоматически.

### Жёлтый или оранжевый

Используется для:

- необходимости проверки;
- предупреждения;
- ожидания согласования;
- неполных данных;
- потенциальной проблемы.

### Красный

Используется для:

- блокирующей ошибки;
- просрочки;
- невозможности продолжить;
- критической ошибки OCR;
- критической ошибки импорта;
- опасного действия.

### Синий или циан

Используется для:

- системной информации;
- OCR и автоматической обработки;
- фонового процесса;
- нейтральной автоматизации.

### Серый

Используется для:

- нейтрального состояния;
- вторичного текста;
- отключённых действий;
- вспомогательной информации.

## 11. Кнопки и действия

Используются три уровня действий.

### Primary

Одно главное действие страницы.

Примеры:

- «Загрузить документ»;
- «Проверить реестр»;
- «Подтвердить»;
- «Сохранить»;
- «Создать реестр».

### Secondary

Поддерживающие действия:

- экспорт;
- история;
- фильтры;
- сброс;
- переключение представления;
- открытие справочника.

### Tertiary, Ghost и Icon

Используются для вторичных строковых операций.

В таблице рекомендуется:

- одно видимое основное действие;
- остальные операции в меню `⋮`.

Удаление и другие опасные операции визуально отделяются от
обычных действий.

## 12. Формы и фильтры

Все формы используют единые:

- высоты полей;
- label;
- placeholder;
- focus-состояния;
- error-состояния;
- сообщения валидации;
- внутренние отступы;
- размеры кнопок.

FilterPanel должен:

- быть компактным;
- не скрывать основной контент;
- поддерживать сброс;
- сохранять значения при переходах;
- иметь понятный блок дополнительных фильтров;
- поддерживать будущие сохранённые представления.

## 13. Статусы

Статусы должны иметь единые:

- названия;
- цвета;
- размеры;
- форму;
- отображение в таблицах;
- отображение в карточках;
- отображение на dashboard;
- отображение в реестрах.

Целевой бизнес-workflow документов:

1. Новый;
2. В работе;
3. На согласовании;
4. Утверждён;
5. Оплачен.

Технические состояния OCR, импорта и фоновых заданий не должны
подменять бизнес-статус документа.

## 14. Таблицы

### Desktop

На широком экране используется полноценная таблица.

Требования:

- соответствие заголовков и колонок;
- semantic-классы;
- суммы выравниваются вправо;
- tabular numbers;
- отдельные колонки статуса, оплаты и действий;
- компактные строковые действия;
- умеренный hover;
- единая высота строк;
- отсутствие конфликтующих глобальных nth-child-контрактов.

### Tablet

На планшетных и небольших ноутбучных ширинах допускается
горизонтальная прокрутка только внутри table container.

Вся страница не должна получать горизонтальный скролл.

### Mobile

На мобильных ширинах таблица преобразуется в карточки.

Карточка документа должна показывать:

- тип и номер;
- контрагента;
- сумму;
- остаток;
- плановую дату;
- статус;
- ответственное лицо при наличии;
- основное действие;
- меню дополнительных действий.

Широкая desktop-таблица с минимальной шириной 900 px и более
не считается окончательной мобильной реализацией.

## 19. Технические правила

- Inline CSS не используется.
- Стили размещаются в модульных CSS-файлах.
- Изменения ограничиваются semantic page scope.
- Перед visual-изменением добавляется semantic scope.
- Новые глобальные nth-child-контракты не создаются.
- Глобальные `:has()`-правила для бизнес-страниц не добавляются.
- Маршруты и формы не меняются ради оформления.
- Важные структуры защищаются regression tests.
- Legacy CSS не удаляется массово одним коммитом.
- Полный test suite в feature-ветке запускается один раз перед release.
- При merge в develop и main выполняются быстрые проверки.
- Production Django-команды используют `config.settings.production`.
- Production collectstatic запускается с явным production settings.
- Визуальная проверка выполняется на утверждённых ширинах.

## 20. Критерии принятия страницы

Страница считается переведённой на Design Contract v1, когда:

- использует один из трёх workspace-шаблонов;
- имеет единый PageHeader;
- использует общие кнопки, поля, карточки и statuses;
- не содержит inline CSS;
- не создаёт горизонтальный скролл всей страницы;
- имеет принятый desktop-режим;
- имеет принятый tablet-режим;
- имеет принятый mobile-режим;
- проходит structural regression tests;
- проходит Django check;
- проходит diff check;
- визуально принята на контрольных ширинах;
- не изменяет бизнес-логику без отдельного этапа.

Semantic commit сохраняется отдельно и не переписывается.

не принят как окончательный visual-контракт. Он сохранён во внешнем

перенесён в эталонную ветку страницы «Документы к оплате» отдельным
контролируемым шагом.
